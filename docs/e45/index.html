If the portal says "Predicted values must be in range [0, 1]"

That error has exactly two causes, both reproduced and eliminated here:

  • The nodata sentinel. training_features.tif stores −3.4028235e+38 outside the survey area. Anything built by stacking that raster wholesale carries values near −10³⁸, which are outside [0, 1].
  • NaN fails a numeric range test. 0 <= nan <= 1 evaluates to False. A validator that range-tests the entire array rejects a NaN-outside file — even though the organizers' own sample_submission.tif is NaN-outside and the problem description says data outside the bounds should be "null or nan".

So two encodings are published, and the choice is yours rather than the writer's: the primary file matches the official template (NaN outside), and the all-finite twin sets every cell to a value in [0, 1] with no NaN at all. Both contain the same 40,000 predictions. Every file here is asserted before writing: single band, float32, template CRS and transform, zero sentinels anywhere, all finite in-footprint values in [0, 1].

Why the file is built this way — the metric, and the rule that decides everything

The published metric is a distance-weighted Tversky index with a triangular kernel of 300 m (3 pixels), α = 0.2 on false positives and β = 0.8 on false negatives:

TP_w = Σ_{g∈G} max_{x: d(x,g)≤R} p(x)·k(d(x,g))
FP_w = Σ_{x: p(x)>0} p(x)·[1 − max_{g∈G} k(d(x,g))]           k(d) = max(1 − d/300m, 0)
FN_w = Σ_{g∈G} [1 − max_{x: d(x,g)≤R} p(x)·k(d(x,g))]
DTI  = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w + ε)

Two exact reductions follow, and both are used everywhere in this project. Writing T = TP_w, F = FP_w, K = |G|:

FN_w = K − T                        (the kernel is 0 beyond R, so both sums maximise alike)
DTI  = T / (0.2·(T+F) + 0.8·K)      equivalently   1/DTI = 0.2 + 0.2·(F/T) + 0.8·(K/T)

The marginal theorem — this is the whole emission rule

Add one unit of prediction mass at a pixel whose realised kernel weight is w = max_g k(d(x,g)). It raises F by exactly 1 − w (the mass is either outside every kernel, or it displaces mass already counted) and raises T by at most w. In the best case,

d(denominator) = 0.2·(w + 1 − w) = 0.2      — independent of where the mass lands

so the added mass pays for itself iff w > 0.2·DTI. At DTI = 0.26 the bar is 0.052; at 0.2778 it is 0.0556; at 0.3195 it is 0.0639; at 0.3262 it is 0.0652. A dot is worth emitting only if it sits within ≈282 m of a hidden truth pixel. Nothing else in the metric matters — not the number of dots, not the emission density, not how the raster looks.

The masking rule makes the target explicit

DrivenData staff answered this on the forum on 2026-09-16 (thread 11516):

"Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms." … "Re-evaluation will also mask/exclude the existing USGS/INGENIOUS faults."

Consequence, and it is decisive: mass placed on the mapped catalogue earns nothing and costs nothing. The entire game is placing mass off the catalogue, within 300 m of faults that are in no public database. Every number on this page is computed on that domain.

Method — tip extension as a survival function

A fault is a finite rupture surface that grows by tip propagation until it meets another fault or the driving stress is relieved. A mapper, though, stops drawing at the last pixel where the evidence is unambiguous. Those two stopping rules differ, and the difference — the tip-extension length — is exactly the population in which a "new fault" enters a catalogue. So the extension length is a time-to-event variable, and it is estimated here as one.

3,1998-connected segments (median length 12 px)

The sample, the event and the censor

  • Sample: for every tip, the along-strike distance to the nearest pixel of a different catalogue segment, searched inside a ±15° cone about that tip's own outward strike.
  • Event: a different segment is reached inside the 120 px window.
  • Censor: nothing is reached — right-censored at 120 px.

The 703 censored tips are precisely the ones with the largest gaps, which is why the naive mean of the observed gaps is biased low, and why the product-limit estimator of Kaplan & Meier (1958) is the right tool rather than a fixed search radius. Fitted curve (genuine sample, gaps > 2 px):

Turning the curve into an emission budget

A dot at along-strike distance e from a tip earns credit when the next along-trend structure lies within the kernel window, so its expected realised weight is

E[w](e) = 0.5 · [ Ŝ(e − 3) − Ŝ(e + 3) ]

Evaluating that against the metric's own bar of 0.2 × 0.30 = 0.06 gives e* = 11 px = 1,100 m: beyond that the expectation falls below what any added mass can pay for. That number is not tuned; it is the intersection of the fitted curve and the metric.

Which of the 19 bands can actually see a fault?

Answered by measurement, because the answer is not obvious and it rules out a whole family of ideas. ρ(1 km) is the correlation between a pixel and the pixel 1 km away: a plane with ρ near 1 is regionally smooth and physically cannot satisfy a 300 m kernel. mean |∂/∂y| is the mean forward difference along the north axis, in units of the band's own standard deviation per pixel. Every mass column is the fraction of that plane's strongest 40,000 pixels — the same mass the shipped submission emits — that land within 300 m of a mapped fault, against a measured random baseline of 8.6 % (the fraction of the footprint within 300 m of the catalogue).

The flank decision: two files, one switch, and no instrument that can judge it

The shipped file excludes every pixel within 200 m of a mapped catalogue fault. That is a scientific claim, not a detail: it says a hidden fault is not in the immediate neighbourhood of an already-mapped one. The alternative claim is equally defensible — hidden faults are commonly parallel splays, unmapped strands inside a mapped corridor, or tip zones, all of which live in that very ring. So the switch was built as a parameter (--flank-px) and both settings were measured at the identical 40,000-pixel mass.

The leakage-controlled blocked holdout in §Holdout could, and it agreed with a much larger margin: H48b 0.030215 vs H48 0.006813, beating the random control in 9 of 11 blocks against 2 of 11. Excluding the 200 m ring around every mapped fault — a rule that looked prudent because catalogue pixels are masked and the penumbra is where false positives are charged — removed the field's strongest pixels and cost 4.4×. The rule is documented and kept as --flank-px, not deleted.

The reading of this table that would have been wrong. The instrument's truth is the mapped catalogue — and the mapped catalogue is the one thing the organizers mask out of the real score (official clarification, thread 11516). The instrument is therefore at its most wrong exactly where these two files differ: it rewards proximity to mapped faults, while the real metric neither rewards nor punishes the mapped pixels themselves and charges a false-positive penalty precisely in the 0–300 m penumbra where H48b places more mass. A 14-point gap on an instrument with a known, measured inversion against live leaderboard order (see §Holdout) is not evidence that H48b scores better in the competition. It is evidence that the two files differ.

What is established: both are format-valid, both are unique against the 69 earlier rasters available for comparison (max support-Jaccard 0.016 and 0.017), and they agree on 33,628 of 40,000 pixels, so the choice is a genuine 6,372-pixel decision rather than a different project. Publishing both, with the switch documented, is the honest move; picking one and claiming the instrument had chosen would not be.

Validation — and why the result is a refusal, not a win

Per the brief, the top candidate must be validated on a spatially-blocked holdout before a submission slot is spent. The grid is cut into a 4 × 4 lattice; for each fold the block's catalogue pixels are withheld and every part of the pipeline is rebuilt without them — segments touching the block are dropped whole, the tip gap sample is re-measured, the Kaplan–Meier curve is re-fitted — and the emission is still painted over the whole map, because that is the competition's shape: you do not know where the scored faults are.

Two findings, and both matter more than the score.

1. Neither arm beat the holdout best, so both are published under HOLD. d2.8 sits at 0.0634 and neither file reaches it (0 of 11 blocks won). What the run did decide is the choice between the two arms: the flanked H48 beat random in only 2 of 11 blocks, the unflanked H48b in 9 of 11, a 4.4× gap in mean DTI. H48b is therefore promoted to the primary download and H48 is kept only as the record of the first attempt. This is a reversal of the initial choice, made because the leakage-controlled run contradicted it — not because a narrative needed one.

2. The instrument cannot rank candidates at all — and this is measured, not asserted. On the catalogue-truth holdout d2.8 (live 0.2600) scores 23× higher than h33-2-b2 (live 0.2778), inverting the live order: 0.0634 vs 0.0028, while live they are 0.2600 vs 0.2778 — a ratio of 0.94. The reason is structural: the truth of this proxy is the visible catalogue, and the organizers mask that catalogue out of the live score entirely. A proxy whose truth is the catalogue rewards covering wherever the catalogue runs; the live truth is a different, sparser set of unmapped faults. Sibling repositories reach the same conclusion by a different route, reporting a leave-one-out Spearman of −0.897 between such a proxy and 16 live scores.

So the honest statement is not "this file failed validation" but "no file can be validated with the instruments available in this environment". One nuance cuts the other way and is worth stating precisely, because it is the reason the H48/H48b comparison is reported at all: in the blocked protocol every prediction is stripped of the block-free catalogue first, so the held-out truth behaves like a genuinely unmapped fault set rather than like the masked catalogue — a closer analogue of the live problem than the whole-map screen is. That makes a same-method, same-style comparison (H48 vs H48b, which agree on 33,628 of 40,000 pixels) more informative than any cross-style comparison here. It does not make it conclusive: the 4.4× gap points in exactly the direction this instrument is biased, so it is strong evidence and not proof. Note the ordering does leave one weak, explicitly non-conclusive signal: the live-best artifact scores lowest on this proxy, and the shipped file scores second-lowest.

Limitations and what would actually move the needle

  1. No live scoring loop. DrivenData's terms forbid automated monitoring and this environment holds no competition account, so every leaderboard statement is a claim. The single highest-value action available is to submit this file manually, once, and return the number — any real number breaks the deadlock that every sibling repository is stuck in.
  2. No instrument that ranks. Until an independent fault inventory (SGMC, or a fresh expert set) can be fetched and validated, candidate selection is an argument, not a measurement.
  3. The supplied features are weak for this task. Best single-plane AUC against the catalogue is 0.61, and 9 of 19 planes carry no information at the kernel's scale. A competitive jump almost certainly requires the 1 m DEM (its links CSV sits behind the competition login) and a real detection model on it, not a better blend of these 19 planes.
  4. No GPU and no training loop, so the reference solution's CNN is out of reach here; only CPU-feasible detectors are represented.
  5. Downscaling LiDAR to 100 m discards the signal that matters. A sub-metre scarp throw averages away at 100 m, yet the competition's grid is fixed. The 1 m DEM is the one input that could change this.
