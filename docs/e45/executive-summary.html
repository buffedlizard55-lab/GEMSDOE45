What was found, in the order it matters

  1. The metric is verified, not assumed. src/gems45/metric.py reproduces the organizers' own worked example to 0.602652 (page states 0.60), and agrees with a literal O(N_truth × N_pred) brute-force transcription on random rasters.
  2. Known catalogue faults are masked out of scoring — officially. DrivenData staff: "Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms", in both rounds. So mass on the mapped catalogue earns nothing and costs nothing, and the entire problem is placing mass off-catalogue.
  3. There is one emission rule, and it is derived. Adding a unit of mass at a pixel of realised kernel weight w raises the denominator by exactly α = 0.2 wherever it lands, so it pays iff w > 0.2 · DTI. At DTI 0.30 that is within ≈282 m of a hidden truth pixel. Nothing else — not dot count, not density — enters the metric.
  4. Nine of the nineteen supplied bands cannot see a 300 m fault. The three geodetic strain-rate bands and the earthquake bands are regional fields (ρ(1 km) ≥ 0.98), so a strain-rate ridge detector is not a failed idea but an impossible one at this resolution. The best single plane is topographic slope (2.8× background enrichment); mag_anom is anti-correlated with the catalogue. tc also carries 12 nodata sentinels inside the nominal footprint (IR-45-002).
  5. The novel contribution: tip extension as a survival function. The catalogue is 3,199 short segments, not long traces. For each of 3,866 tips we measure the along-strike relay gap — 3,163 events, 703 right-censored — and fit the Kaplan–Meier product-limit curve. Each tip is extended by its own length from that curve; the lengths span 2–11 px over 10 distinct values, so they provably vary by fault instead of collapsing to a constant.
  6. And the honest refusal. On the only spatially-blocked instrument this environment can run, the shipped file does not beat the incumbent: 0.0068 against d2.8's 0.0634 and a random control's 0.0127. Worse, that instrument inverts the live order by 23× (d2.8 live 0.2600 vs h33-2-b2 live 0.2778), because its truth is the very catalogue the organizers mask out. So the file ships as a candidate under HOLD, and the finding recorded is that no candidate can be validated with the instruments available here.

If the portal says "Predicted values must be in range [0, 1]"

Two causes, both reproduced and eliminated:

  • training_features.tif stores −3.4028235e+38 outside the survey, so any raster stacked from it wholesale carries values near −10³⁸.
  • 0 <= nan <= 1 is False, so a validator that range-tests the whole array rejects a NaN-outside file — even though the organizers' own sample_submission.tif uses that encoding and the spec says outside-bounds data should be "null or nan".

Hence two files, same 40,000 predictions: the primary matches the official template (NaN outside), and the all-finite twin has every cell in [0, 1] with no NaN at all. Every file published here is asserted before writing: single band, float32, template CRS and transform, zero sentinels anywhere, all finite in-footprint values in [0, 1].
